# 02. 抽象化メソドロジー: AI支援型インフラ調査の汎用フレームワーク

> [01-case-study-deep-dive.md](./01-case-study-deep-dive.md) のGoogle固有事例から、**ターゲット非依存**の再利用可能な原理を抽出する。
> Google APIに限らず、任意のサービス(Web/モバイル/クラウド)のインフラ調査に適用できる形に一般化する。

---

## 0. 中心思想: 「広さは決定的に、深さは意味的に」

```
        ┌──────────────────────────────────────────────┐
        │  決定的レイヤ (Deterministic)                  │
        │  = 広さ・収集・正規化・検証・反ハルシネーション │
        │     再現可能で監査可能。スコープを強制する。     │
        └──────────────────────────────────────────────┘
                          ▲   ▼  (構造化された証拠 / 操作)
        ┌──────────────────────────────────────────────┐
        │  意味的レイヤ (Semantic / AI)                  │
        │  = 方針決定・分類・仮説生成・深掘り判断          │
        │     「何が異常か」「次に何を見るか」を推論する。  │
        └──────────────────────────────────────────────┘
```

**鉄則**: AIに広さ(全件走査)や検証(本当にアクセスできたか)をやらせない。AIには**意味判断と方向決定**だけをやらせる。

---

## 汎用パイプライン: 7つの抽象フェーズ

各フェーズを「目的 / 一般原理 / 入力 / 出力 / 適用例」で定義する。Google固有の語彙(FPA, visibility label等)は、右側に**一般化した概念**を併記する。

### Phase A — 資産ハーベスティング (Asset Harvesting) 〔広さ〕

| 項目 | 内容 |
|------|------|
| 目的 | 調査の「燃料」となる資産(クレデンシャル・成果物・エンドポイント)を、**全配布チャネル × 全履歴**から網羅収集する。 |
| 一般原理 | 単一スナップショットは不十分。**チャネル横断 + 履歴横断**で集める。資産は**メタデータ(制約・出所)込み**で保存する。 |
| Google事例 | APK 61,200版 / iOS IPA / バイナリ / Web傍受 2,800ドメイン → 3,600キー + キー制約 |
| 一般化した収集源 | モバイルアプリ(APK/IPA)・JSバンドル/sourcemap・公開リポジトリ・コンテナイメージ・CT(証明書透明性)ログ・DNS・WHOIS・Web検索・パブリッククラウドストレージ |
| 抽出対象 | APIキー/トークン・エンドポイントURL・サブドメイン・第三者SDK・バックエンドホスト・project/account識別子 |
| 出力 | **資産インベントリ**(各資産に出所・制約・発見時刻のprovenance付き) |

> 抽象パターン #1: **Multi-channel, multi-version harvesting**。「相手が外に出している全てのバイナリ/コードを集めて中を見る」。

---

### Phase B — スコープ確定 (Scope Resolution) 〔安全 + 集中〕

| 項目 | 内容 |
|------|------|
| 目的 | 集めた資産・発見対象が**本当に調査対象(許可範囲)に属するか**をプログラム的・決定的に判定する。 |
| 一般原理 | 所有判定は**AIや人手の勘ではなく決定的手続き**で。これは「対象外への誤爆防止(安全)」と「無関係資産の除外(集中)」を同時に満たす。 |
| Google事例 | エラーからproject番号抽出 → Cloud Marketplace APIで所有ドメイン確認 → google.com以外を破棄 |
| 一般化した判定材料 | WHOIS/RDAP・ASN/IP範囲・証明書のSAN・DNS所有権・組織OSINT |
| 出力 | **スコープ確定済み対象リスト** + **allowlist**(以降の全アクションがこれを強制参照) |

> 抽象パターン #2: **Programmatic ownership filtering**。エラーメッセージは所有判定の情報源にもなる(「エラー=漏洩源」)。

---

### Phase C — 表層列挙 (Surface Enumeration) 〔広さ〕

| 項目 | 内容 |
|------|------|
| 目的 | 攻撃対象領域(エンドポイント・サービス・隠れ面)を炙り出す。 |
| 一般原理(3本柱) | (1)**機械可読仕様の入手**、(2)**パラメータ操作で隠れ面を露出**、(3)**シグネチャで生存判定**。 |
| (1) 機械可読仕様 | discovery document / OpenAPI / GraphQL introspection / proto。**仕様を持つことが後の全自動化の前提**。 |
| (2) 隠れ面の露出 | リクエストパラメータ(例: `labels=GOOGLE_INTERNAL`)で応答内容が変わる → **既知パラメータ全種 × 全クレデンシャルを総当たり**(組合せ爆発=自動化必須)。 |
| (3) 生存判定 | レスポンスの**シグネチャ**(serverヘッダ ESF/GSE/HTTPServer2 等、応答サイズ差、特徴的エラー)で「本物の稼働サービス」を識別。 |
| ホスト発見源 | CTログ・パッシブDNS・キーワードからのブルートフォース生成 |
| 出力 | **エンドポイント目録**(仕様・生存状態・要求クレデンシャル付き) |

> 抽象パターン #3: **Spec-first surface mapping**。「叩く前に仕様を手に入れる」。隠れ面は「同じ要求 + 異なるパラメータ/権限」で差分として現れる。

---

### Phase D — プロトコル/認証の解明 (Protocol Reverse Engineering) 〔深さの前提〕

| 項目 | 内容 |
|------|------|
| 目的 | 対象を「正規ユーザーとして正しく叩く」ために、認証・認可・検証の仕組みを完全に理解する。 |
| 一般原理 | **リバースする前に、漏れた仕様を探せ**。sourcemap・デバッグシンボル・公開ソース・proto定義は、リバースを丸ごとスキップさせる。 |
| Google事例 | sourcemap漏洩(gapix)からFPA v2を実装。トークン形式・キー制約4種・10層検証パイプラインを解明。 |
| 一般化した成果物 | **認証クライアントの実装** + **検証パイプラインの地図**(「リクエストが通過する全チェックの順序」)。この地図が「どこに認可の穴があるか」の探索空間になる。 |
| 出力 | **認証モジュール**(トークン生成・必要ヘッダ付与)+ **検証レイヤ一覧** |

> 抽象パターン #4: **Leaked-spec-first auth modeling**。認可バグは多くが「最終段(メソッド単位)の認可欠落」。そこに到達するには前段の全チェックを満たす必要がある。

---

### Phase E — 正規化レイヤ (Normalization) 〔自動化の土台・最重要〕

| 項目 | 内容 |
|------|------|
| 目的 | 不均質なターゲットを、**単一の一様な操作**に落とし込む。 |
| 一般原理 | 仕様(Phase C)+ 認証(Phase D)を組合せ、`probe(target, operation, params) → 構造化応答` という**統一インターフェース**を作る。これ無しにAI自動化は載らない。 |
| Google事例 | カスタムAPI Explorer(discovery docをクライアント解析 + FPA自動付与 + JSON自動構築)。検証[1]〜[9]を自動で満たす装置。 |
| 出力 | **統一プローブAPI**(全ターゲットを同じ形で叩け、構造化応答を返す) |

> 抽象パターン #5: **Uniform probe interface**。「一度 `probe()` に正規化すれば、その上に任意の自動化(AI/総当たり/差分検出)を載せられる」。これがパイプライン全体の要石。

---

### Phase F — AI推論オーケストレーション (Semantic Orchestration) 〔深さ〕

正規化された `probe()` の上に、AIを**意味判断エンジン**として載せる。設計の核は「AIに何をさせ、何をさせないか」の線引き。

#### F-1. ツール設計(AIに与える操作)
| ツール類型 | 役割 | 反ハルシネーション設計 |
|-----------|------|----------------------|
| **probe系** | 対象を叩く。**operation_idを返す** | 入力を最小化(裏で文脈を追跡)してAIの捏造余地を削る |
| **report系** | 発見を記録。**probe由来のoperation_id引用を必須** | 全主張を「実際に送受信したデータ」に紐付け(捏造不可) |
| **context系** | スコープ外要素のスキーマ/文脈を取得 | 文脈取得前のprobeを禁止 |
| **complete系** | 完了宣言。**システムが網羅性を検証** | AIの早期離脱を防止 |

#### F-2. コンテキスト管理 = 分割 + 引き継ぎ
- 大きな対象をAIに**論理グループへ分類**させる(根拠付き)。
- 1グループ=1集中セッション。
- **前グループの発見を次グループへ引き継ぐ**。
- → 「浅く広く分類 → 各グループを深掘り」という二段構え。

#### F-3. 応答の意味正規化(ノイズ→信号)
- 生エラーを渡さず、**意味タイプ**に変換(例: 曖昧な404 → 「権限ラベル不足」)。
- AIは「メソッドが無い」と「権限が足りない」を区別できて初めて正しく深掘りできる。

#### F-4. 差分抽出(複数クレデンシャルprobing)
- **同一プローブを全クレデンシャルで投げ、応答ハッシュでグルーピング**。
- 「大半で同一」を捨て、**ユニーク応答(=権限差で挙動が変わった)だけを信号化**。
- 認可の穴の本質=「誰かには見えて誰かには見えない」を直接検出する。

> 抽象パターン #6: **AI = reasoner, code = evidence/breadth/scope**。
> 抽象パターン #7: **Classify-then-deepen**(浅く広く分類してから深掘り)。
> 抽象パターン #8: **Differential probing**(複数視点の応答差分だけを信号にする)。

---

### Phase G — Signal/Noise定義と反復 (Refinement) 〔精度〕

| 項目 | 内容 |
|------|------|
| 目的 | 「何が発見(signal)で、何がノイズか」を厳密に定義し、実用精度に到達する。 |
| 一般原理 | 自動化の成否は発見ロジックより**ノイズの定義**で決まる。**「何を報告しないか」を書くこと**が最重要。 |
| 定義すべき項目 | (a)**正典の境界**(存在する対象の集合を固定し空想を抑制)、(b)**手法 vs 発見の区別**(列挙できること自体は発見ではない)、(c)**存在オラクルの除外**(機密漏洩を伴わない有無判別は非報告)、(d)**重大度較正**(どのエラー/状態を無視するか)、(e)**証拠の強制**(全主張に実データ参照)。 |
| 反復 | これらは一発で決まらない。**実走 → ノイズ観察 → ルール追記** を繰り返して収束させる。 |

> 抽象パターン #9: **Noise-first prompt engineering**。「報告しない条件」の定義が精度を作る。

## 横断原則: 発見の還流(再帰的深掘り)

```
Phase F/D で得た新ホスト・新識別子・SA名・project番号・新ドメイン
        └──────── seed として Phase B/C に再投入 ────────┘
                  → 対象が自己増殖的に拡大(自動的な「方向決定」)
```

これが「**調査の方向性を自動で決めて深掘りする**」の正体: 新しい発見が新しいシードになり、収束(深さ上限/予算/新規発見ゼロ)まで回る。**深掘りの方向はAIが選ぶが、ループの制御は決定的コードが持つ**。

---

## 横断原則: 安全・倫理(全フェーズに常駐)

| 機構 | 内容 |
|------|------|
| スコープ allowlist | Phase Bで確定。**全ネットワークアクションがこれを強制参照**。範囲外はブロック。 |
| レート制限・予算 | 最大リクエスト数・最大深さ・時間/コスト上限。 |
| 監査ログ | 全アクション(probe・取得・AI判断)を記録。再現可能性=反ハルシネーションと同根。 |
| サンドボックス | 取得成果物(APK等)の解析は隔離環境で。 |
| 承認ポリシー | 能動的・不可逆な操作はallowlist/承認制。 |

## 抽象パターン総覧(チートシート)

| # | パターン | 一言 |
|---|---------|------|
| 1 | Multi-channel/version harvesting | 相手の全バイナリ・全履歴を集めて中を見る |
| 2 | Programmatic ownership filtering | 所有判定は決定的に。エラーは漏洩源 |
| 3 | Spec-first surface mapping | 叩く前に機械可読仕様を取る。隠れ面はパラメータ差分で出る |
| 4 | Leaked-spec-first auth modeling | リバース前に漏れた仕様を探す。検証順序を地図化 |
| 5 | Uniform probe interface | 不均質な対象を単一 `probe()` に正規化(自動化の土台) |
| 6 | AI=reasoner / code=evidence | 意味判断はAI、広さ・検証・反捏造はコード |
| 7 | Classify-then-deepen | 浅く広く分類 → 各単位を深掘り |
| 8 | Differential probing | 複数視点の応答差分だけを信号にする |
| 9 | Noise-first prompting | 「報告しない条件」を定義して精度を作る |
| 10 | Recursive seed reflux | 発見をシードに還流して自己増殖的に深掘り |
